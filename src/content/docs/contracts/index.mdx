MIST's contracts are written in Solidity and built with Foundry. Three kinds of contract carry the protocol: the Chamber, Reserves and middlewares. Two more support them: the verifier and the registrar.

| Contract | Role | Entry points |
| --- | --- | --- |
| `Chamber` | Verifies each spend and applies it to state. Holds no assets | `deposit`, `handleZkp`, `approveDeposits`, `rejectDeposits`, `reclaimDeposit`, `setDepositRefundTo`. Owner: `registerReserve`, `proposeVerifier`, `executeVerifierUpdate`, `setGuardian`. Guardian: `pauseInflows`, `pauseSpends` |
| `Reserve` | Holds the assets of its notes under one rule set. Moves them only when the Chamber asks | `deposit` and `withdraw` (Chamber only). `addUser` and `removeUser` (`USERS`), `setScreener` (`SCREENING`), `setAssetMinDeposit` (`ASSETS`), `updateAuditorKey` (`METADATA`). Admin: `grantPermission`, `revokePermission`, `transferAdmin` |
| `ChamberVerifier` | The Groth16 verifier, generated by gnark. Accepts compressed and uncompressed proofs and rejects any public input at or above the field order | `verifyProof`, `verifyCompressedProof` |
| `ManagerSigRegistrar` | The registrar for every Reserve. Anyone can submit a registration that carries the signature of a `USERS` holder | `registerUser(reserve, leaf, deadline, signer, signature)`, `revoke(reserve, leaf)` |

Middlewares are contracts that own notes. A note owned by a middleware is spent with `auth_done = 0`, so only the middleware can submit the spend, and it decides first whether the spend happens. None exists yet.

## The flows

1. **Deposit.** `Chamber.deposit(reserve, ownerCommitment, amount, asset)` takes no proof. An overload adds a trailing `refundTo`. Both return `(noteHash, depositId)`, and `depositId` is 0 when the Reserve has no screener. The depositor approves the Reserve, which pulls the asset. The asset must be listed at the Reserve, and the amount the Reserve received must meet its minimum deposit. At a Reserve with a screener the note is queued, and the screener calls `approveDeposits` or `rejectDeposits`. `approveDeposits` skips ids that are not pending and rejects a duplicate note instead of reverting the batch. While the deposit is pending, only the depositor can reclaim it, and the funds return to the depositor. The depositor can change `refundTo` with `setDepositRefundTo` until the screener decides. Once the deposit is rejected, the depositor or `refundTo` can reclaim it, and the funds go to `refundTo`. Reclaiming is never paused.
2. **Transfer.** `Chamber.handleZkp(proof, publicInputs, auditorCommitments)` reverts while spends are paused. Otherwise it verifies the proof, checks the roots and the authorisation, marks both nullifiers spent and appends both new notes. No assets move.
3. **Withdrawal.** The same call with a non-zero `withdraw_amount`. After every state write the Chamber calls `Reserve.withdraw`, which pays the recipient.
4. **Registration.** A member's leaf is `H2(owner, userKeyExchange)`, computed off-chain. `ManagerSigRegistrar.registerUser` checks the EIP-712 signature of a `USERS` holder, by ECDSA or ERC-1271, and calls `Reserve.addUser`. The signed message binds a deadline, the signer and the signer's permission epoch, and the leaf's nonce, which moves on every registration and removal. A removed user therefore cannot return with an older signature, and a signer that lost `USERS` cannot use its old ones. Any `USERS` holder can `revoke` every outstanding signature for a leaf. `Reserve.removeUser(index)` zeroes a user's leaf, and it reverts if that would empty the users tree.

:::caution[Assets sent to a Reserve directly are lost]
A Reserve takes assets only through `Chamber.deposit`. Assets sent to a Reserve address by a plain transfer are unrecoverable.
:::

## Timelocks and pauses

- **Verifier.** `proposeVerifier` queues a new verifier, `executeVerifierUpdate` makes it live after 7 days if its code hash is unchanged, and `cancelVerifierUpdate` drops it.
- **Ownership.** `transferOwnership` queues a new owner, who accepts after 7 days. `renounceOwnership` always reverts.
- **Guardian.** `pauseInflows` stops `deposit` and `approveDeposits` until the guardian or owner unpauses. `pauseSpends` stops `handleZkp` for 3 days, and the next pause can start no sooner than 7 days after the last one ended.

## Events

The Chamber emits `NoteAppended` for every note it adds, `TxTreeOpened` when a tree fills and the next opens, and `PrivateTransfer` for a spend with commitments. Deposit screening emits `DepositQueued`, `DepositRefundToSet`, `DepositApproved`, `DepositRejected`, `DepositDuplicateRejected` and `DepositReclaimed`. State changes emit `ReserveRegistered`, `ReserveConfigUpdated`, `ZkStateRootUpdated`, `ZkStateHistoryRetired`, `ReserveScreenerSet`, `ReserveAssetMinDepositSet`, `GuardianSet`, the pause events, `OwnershipTransferQueued` and the `VerifierUpdate` events. A Reserve emits `UserRegistered`, `UserRemoved`, `AuditorKeyUpdated`, `PermissionGranted`, `PermissionRevoked` and the admin transfer events. The registrar emits `SignaturesRevoked`.

`getTxArray(offset, limit)` returns a page of the note history across every tree.

## Toolchain

The contracts are pinned to solc 0.8.35, the Paris EVM and 200 optimizer runs. `ChamberVerifier.sol` is generated by gnark from the circuit and is never edited by hand.

## Source

The contracts are in `core/contracts/src`. The [specification](https://github.com/mistcash/mist/blob/main/spec/02_smart_contract.md) defines their state, actions and trusted roles.
