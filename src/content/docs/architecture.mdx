MIST has one Chamber per network, any number of Reserves, one circuit and a generated verifier. Funds sit in Reserves. The record of who owns what sits in the Chamber.

<Architecture />

## Components

| Component | Role | Source |
| --- | --- | --- |
| Chamber | The state engine. Verifies each spend's proof and applies it. Keeps the transactions tree, the spent nullifiers, the zkState tree and the Reserve registry. Never holds assets | `core/contracts/src/Chamber.sol` |
| Reserve | Holds the assets of the notes in its custody under one compliance rule set. Moves assets only when the Chamber asks | `core/contracts/src/Reserve.sol` |
| ChamberVerifier | The Groth16 verifier, generated by gnark for the circuit's 14 public inputs | `core/contracts/src/ChamberVerifier.sol` |
| ManagerSigRegistrar | The interim registrar. Adds a user to a Reserve on the manager's EIP-712 signature | `core/contracts/src/ManagerSigRegistrar.sol` |
| PrimaryTransactionCircuit | The one circuit. Every spend is a proof of it | `core/circuits/src/primary.go` |
| Middleware | A contract that owns notes and adds its own rules before it spends them. The Chamber supports middlewares through ordinary note ownership. None exists yet | Not part of core |

[Contracts](/contracts/) and [Circuits](/circuits/) cover each in turn.

## Separate custody

A network can have as many Reserves as it needs, each standing for one rule set: for example every user passed KYC, every wallet passes an AML check, or no extra conditions. A note never leaves its Reserve except as a public withdrawal, so funds governed by one rule set stay apart from funds that follow another.

Funds never touch the Chamber. ERC-20 `Transfer` events show only movements to and from Reserves. Suspicious activity at one Reserve affects that Reserve's funds and no other.

|  | Monolithic contract | Separate Reserves |
| --- | --- | --- |
| Deposit | Full recipient privacy | Full recipient privacy |
| Withdrawal | Sender hidden among every note in MIST | Sender hidden among the notes of its own Reserve |
| Payment inside MIST | Sender and receiver hidden among every note in MIST | Sender and receiver hidden among every note in MIST |

## State in the Chamber

- **Transactions tree.** An append-only Merkle tree of notes. Every root it has had stays valid, so a note stays spendable after the tree has moved on.
- **Nullifier map.** Every nullifier a spend has published.
- **zkState tree.** One leaf per Reserve: `H3(reserve, reserve_config, users_root)`. Only the current root is valid.
- **Reserve registry.** Each Reserve's manager, zkState leaf and deposit screener.
- **Pending deposits.** Deposits waiting for a screener, keyed by deposit id.
- **Private transaction records.** The identifier and the six published commitment elements of each spend that has them.

Both trees have depth 10 and four children per node, so each holds 4^10 leaves.

## Cryptography

| Primitive | Choice |
| --- | --- |
| Curve | BN254, the curve behind the EVM's pairing precompiles |
| Proof system | Groth16, with the circuit written in gnark. The keys come from a single-party setup |
| Hash | Poseidon2 over the BN254 scalar field: 8 full rounds, 56 partial rounds, S-box exponent 5 |
| Encryption | Hash-and-Add, a stream cipher on the width-4 Poseidon2 permutation |
| Merkle trees | Depth 10, four children per node. A node hashes its children in sorted order |

The circuit does no elliptic-curve operations, and no MIST protocol key lives on a curve.

## Roles

| Role | Powers | Limits |
| --- | --- | --- |
| Chamber owner | Registers every Reserve and picks its manager. Replaces the verifier with `setVerifier`, at any time | A verifier that accepts anything authorises the withdrawal of everything held. The role is explicit and privileged in a pre-production deployment. A timelock on verifier changes is planned |
| Reserve manager | Updates the Reserve metadata, sets the registrar and sets the deposit screener. At a Reserve with members, reads their spends | Cannot move funds. The specification fixes one manager per Reserve, and plans an admin with per-permission roles |
| Registrar | Set by the manager. Decides who joins the Reserve's registered users | The specification has no removal of a registered user. Revocation is planned |
| Deposit screener | Set by the manager. Decides which deposits enter the transactions tree | Cannot move funds. A depositor can reclaim a pending or rejected deposit |
| Relayer | Not a role. Anyone can submit an `auth_done = 1` spend | Cannot change it |

## Known limits

- **One zkState root for every Reserve.** Only the current root is accepted. A registration or metadata update at any Reserve replaces it and retires every proof in flight across the protocol.
- **A finite transactions tree.** When the tree is full, appends revert, so every spend reverts, withdrawals included.
- **No emergency pause.** Swapping in a verifier that rejects everything is the only stop.
- **No solvency ledger and no asset allowlist.** The circuit's conservation rule and each Reserve's own balance bound what can leave. The Chamber accepts any ERC-20.

The [specification](https://github.com/mistcash/mist/tree/main/spec) is the document of record, and its implementation status file tracks each limit.
