MIST has one Chamber per network, any number of Reserves, one circuit and a generated verifier. Funds sit in Reserves. The record of who owns what sits in the Chamber.

<Architecture />

## Components

| Component | Role | File |
| --- | --- | --- |
| Chamber | The state engine. Verifies each spend's proof and applies it. Keeps the transactions trees, the spent nullifiers, the zkState tree and the Reserve registry. Never holds assets | `Chamber.sol` |
| Reserve | Holds the assets of the notes in its custody under one compliance rule set. Keeps its registered users and its admin's permissions. Moves assets only when the Chamber asks | `Reserve.sol` |
| ChamberVerifier | The Groth16 verifier, generated by gnark for the circuit's 14 public inputs | `ChamberVerifier.sol` |
| ManagerSigRegistrar | The registrar. Adds a user to a Reserve on the EIP-712 signature of a holder of its USERS permission | `ManagerSigRegistrar.sol` |
| PrimaryTransactionCircuit | The one circuit. Every spend is a proof of it | `primary.go` |
| Middleware | A contract that owns notes and adds its own rules before it spends them. The Chamber supports middlewares through ordinary note ownership. None exists yet | Not part of core |

The contracts are in `core/contracts/src` and the circuit is in `core/circuits/src`. [Contracts](/contracts/) and [Circuits](/circuits/) cover each in turn.

## Separate custody

A network can have as many Reserves as it needs, each standing for one rule set: for example every user passed KYC, every wallet passes an AML check, or no extra conditions. A note never leaves its Reserve except as a public withdrawal, so funds governed by one rule set stay apart from funds that follow another.

Funds never touch the Chamber. ERC-20 `Transfer` events show only movements to and from Reserves. Suspicious activity at one Reserve affects that Reserve's funds and no other.

|  | Monolithic contract | Separate Reserves |
| --- | --- | --- |
| Deposit | Full recipient privacy | Full recipient privacy |
| Withdrawal | Sender hidden among every note in MIST | Sender hidden among the notes of its own Reserve |
| Payment inside MIST | Sender and receiver hidden among every note in MIST | Sender and receiver hidden among every note in MIST |

## State in the Chamber

- **Transactions trees.** Append-only Merkle trees of notes. Each holds 4^10 notes. When one fills, the next opens, and every root any tree has had stays valid, so a note stays spendable after its tree has moved on. A spend proves both inputs against one root.
- **Nullifier map.** Every nullifier a spend has published.
- **zkState tree.** One leaf per Reserve: `H3(reserve, reserve_config, users_root)`. The current root is valid, and a superseded root stays valid for 10 minutes.
- **Reserve registry.** Each registered Reserve's zkState leaf, deposit screener and asset list. An asset is listed with a minimum deposit, and zero means it cannot be deposited.
- **Pending deposits.** Deposits waiting for a screener, keyed by deposit id, each with an optional refund address.
- **Private transaction records.** The identifier and the six published commitment elements of each spend that has them.
- **Pause state.** The guardian, whether inflows are paused and until when spends are paused.

The zkState tree and each transactions tree have depth 10 and four children per node.

## Cryptography

| Primitive | Choice |
| --- | --- |
| Curve | BN254, the curve behind the EVM's pairing precompiles |
| Proof system | Groth16, with the circuit written in gnark. The keys come from a single-party setup |
| Hash | Poseidon2 over the BN254 scalar field: 8 full rounds, 56 partial rounds, S-box exponent 5 |
| Encryption | Hash-and-Add, a stream cipher on the width-4 Poseidon2 permutation |
| Merkle trees | Depth 10, four children per node. A node hashes its children in sorted order |

The circuit does no elliptic-curve operations, and no MIST protocol key lives on a curve.

## Roles

| Role | Powers | Limits |
| --- | --- | --- |
| Chamber owner | Registers every Reserve and names its admin. Proposes a new verifier, which goes live after 7 days and only if its code is unchanged, and can cancel it. Sets or replaces the guardian, which can also be named at construction. Moves ownership in two steps behind a 7-day timelock | Cannot swap the verifier instantly, and cannot renounce ownership. A verifier that accepts anything would authorise the withdrawal of everything held, so the owner should be a multisig |
| Guardian | Pauses `deposit` and `approveDeposits` until unpaused. Pauses spends for at most 3 days, with 7 days between pauses. The owner can also unpause | Cannot stop `reclaimDeposit` or `rejectDeposits`. A spend pause ends on its own and cannot be chained |
| Reserve admin | Named by the Chamber owner. Holds every permission, grants and revokes them, and hands the role to a new admin in two steps | Cannot move funds. Grants survive a handover until the new admin revokes them. The previous admin loses its implicit permissions at the handover |
| Permission holders | `ASSETS`: list and delist assets and set minimum deposits. `USERS`: add and remove registered users. `METADATA`: update the Reserve's auditor key. `SCREENING`: set the deposit screener | Each permission covers only its own action. None can move funds |
| Registrar | A contract or account holding `USERS`. `ManagerSigRegistrar` registers a user when a `USERS` holder signed it | A signature carries a deadline and binds the signer, the signer's permission epoch and the leaf's nonce. A removal or the signer losing `USERS` voids it. Any `USERS` holder can revoke every outstanding signature for a leaf |
| Deposit screener | Set by a `SCREENING` holder. Decides which deposits enter a transactions tree | Cannot move funds. The depositor can reclaim a pending deposit. A rejected one is refunded to the address the deposit named |
| Relayer | Not a role. Anyone can submit an `auth_done = 1` spend | Cannot change it |

## Known limits

- **One zkState root for every Reserve.** A registration, removal or metadata update at any Reserve replaces it. The previous root stays valid for 10 minutes, so a proof in flight survives a change inside that window. The first registration at a Reserve switches messaging on there and retires every older root at once, because older roots have no users root for it.
- **Removal takes effect after the window.** A removed user stays provable until the last root that holds their leaf expires, at most 10 minutes.
- **A removal freezes the removed user's notes.** At a Reserve with members, only members can spend. A removed user's notes there stay unspendable until a `USERS` holder registers the user again. Any single `USERS` holder can make that removal. The exit spend that would let any owner withdraw in public is **Planned**, and core's operations notes say not to deploy to production, or not to let any Reserve remove users, until it lands.
- **Inputs from one tree.** A spend proves both inputs against one transactions root, so it cannot combine notes from different trees. To merge them, the owner first spends one note with a dummy second input, which lands its outputs in the current tree.
- **No solvency ledger.** The circuit's conservation rule and each Reserve's own balance bound what can leave. A Reserve's admin must list only plain assets: never rebasing, fee-on-transfer, blocklisting or upgradeable ones.

The [specification](https://github.com/mistcash/mist/tree/main/spec) is the document of record, and its implementation status file tracks each limit.
