A note is a commitment to an owner, an asset and an amount, held under one Chamber and one Reserve. Every hash in it is Poseidon2 over the BN254 scalar field, and the circuit, the native Go helpers and the Solidity library compute the same values.

## Fields

| Field | Contents |
| --- | --- |
| `chamber` | The Chamber ID, not the bare Chamber address |
| `reserve` | The Reserve contract address |
| `blinding` | A random nonce, the note's spending secret |
| `owner` | A wallet or contract address, or a MIST Address |
| `asset` | The ERC-20 contract address |
| `amount` | Below 2^120. The circuit range-checks it and `Chamber.deposit` requires it |

Addresses enter the field as left-padded big-endian `uint160` values, with no reduction. A 160-bit value is smaller than the field, so nothing wraps.

## Chamber ID

Two chains can host a Chamber at the same address, so a note names its Chamber by ID:

```text
chamber = H2(chainId, chamberAddress)
```

The Chamber computes it in its constructor and stores it as the immutable `chamberId`. The chain ID is frozen at deployment.

## Note hash and nullifier

```text
custody         = H2(chamber, reserve)
ownerCommitment = H2(blinding, owner)
noteHash        = H4(custody, ownerCommitment, asset, amount)
nullifier       = H4(custody, H2(blinding + 1, owner), asset, amount)
```

- **Custody binding.** `H2(chamber, reserve)` locks the note to one Chamber and one Reserve, the only instances that can move it. In the circuit, `chamber` and `reserve` are private inputs of the whole spend, and the binding is computed once for all four notes.
- **Owner commitment.** `H2(blinding, owner)` hides the recipient. Whoever creates a note needs only the commitment, never the recipient's blinding or owner. `Chamber.deposit` takes it as an argument and requires it to be below the field order. The circuit takes each output as an owner commitment and an amount.
- **Note hash.** The leaf appended to the transactions tree. `Chamber.hashNote(chamber_, reserve_, ownerCommitment_, asset_, amount_)` computes it on-chain. A deposited note hashes the amount the Reserve actually received, not the amount requested.
- **Nullifier.** The note hash with the blinding increased by one. A spend publishes it, and the Chamber records it as spent.

The nullifier does not use the MIST Address secret. Two consequences follow:

- **Anyone who knows a note's fields can watch for its spend.** That person can compute the nullifier, but spending still takes the owner's secret or the owner as caller. A sender who built the owner commitment from the recipient's blinding and owner knows every field. The nullifier stays private from the sender only when the recipient picks the blinding and hands over a finished owner commitment.
- **Sequential blindings link notes.** A note's nullifier equals the hash of a note with blinding `b + 1` and otherwise the same fields. A wallet that derives blindings in sequence for repeated notes with the same owner, asset and amount links them. Derive each blinding independently.

## Owners

| Owner | Value | Spent with | Authorised by |
| --- | --- | --- | --- |
| Wallet or contract address | The `uint160` address | `auth_done = 0` | The Chamber, which requires the owner as caller |
| MIST Address | `H2(p, 0x6f776e6572)`, with `p` a secret | `auth_done = 1` | The proof, as knowledge of `p` |

The keyword `0x6f776e6572` is the ASCII string "owner" (478745093490). A MIST Address is a hiding commitment, so publishing it reveals nothing about `p`. [What a spend proves](/circuits/spend/#authorisation) gives both modes in full.

## Poseidon2

Every width uses the same parameters: the BN254 scalar field, 8 full rounds, 56 partial rounds and S-box exponent 5. The round counts are set in `core/circuits/gadgets/gadgets.go` and `core/circuits/lib/hash/poseidon2.go`. The exponent is gnark-crypto's fixed S-box degree for BN254.

Each function feeds an input forward into one element of the final permutation state. The width-4 permutation serves three of them, `H4`, `HM4` and the keystream, told apart only by how the output is read:

| Function | Width | Output | Constraints |
| --- | --- | --- | --- |
| `H2(a, b)` | 2 | `state[1] + b` | 217 |
| `H3(a, b, c)` | 3 | `state[0] + a` | 241 |
| `H4(a, b, c, d)` | 4 | `state[0] + a` | 265 |
| `HM4`, the Merkle node | 4 | `state[0] + state[1]`, over sorted children | 283, selector included |
| Keystream block | 4 | `state[j + 1] - k`, for `j = 0, 1, 2` | 265 per block |

Constraint counts are from core's committed constraint snapshot. Each is measured on a small wrapper circuit that also asserts the result equals a public input, so each figure includes that one constraint.

The output read is the only thing that separates the three width-4 uses: there is no extra input, domain tag or round. The [specification](https://github.com/mistcash/mist/blob/main/spec/01_system_overview.md) gives the argument for why that is enough.

`Fold2` reduces a vector to one element by chaining `H2` from the left: `Fold2(v) = H2(... H2(H2(v0, v1), v2) ..., vn)`.

## Where each hash is used

| Value | Hash |
| --- | --- |
| Chamber ID | `H2(chainId, chamberAddress)` |
| Custody binding | `H2(chamber, reserve)` |
| Owner commitment | `H2(blinding, owner)` |
| Note hash, nullifier | `H4(custody, ...)` |
| MIST Address | `H2(p, 0x6f776e6572)` |
| Reserve config | `H2(keyHash, keyInputPoint)` |
| zkState leaf | `H3(reserve, reserveConfig, usersRoot)` |
| Registered-user leaf | `H2(owner, userKeyExchange)` |
| Messaging key | `H2(userKeyExchange, keyIndex)` |
| `auditor_commitments` | `Fold2([privateTxKey, c0, c1, c2, c3, c4])` |
| Merkle node | `HM4` |

[Merkle trees](/circuits/merkle-trees/) covers `HM4`, and [Reserve messaging](/circuits/reserve-messaging/) the keystream.
